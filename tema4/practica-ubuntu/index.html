    Tema 4. Práctica en Ubuntu: análisis de sockets

    1. Objetivos

    En esta práctica aprenderás a:

    • Consultar los sockets TCP y UDP de un sistema Ubuntu.
    • Identificar los puertos en los que escuchan los servicios.
    • Diferenciar un socket de escucha de una conexión establecida.
    • Iniciar un servidor web temporal y observar su socket.
    • Comprobar el acceso a un servicio mediante curl.
    • Entender cómo afecta la dirección de escucha a la accesibilidad de un servicio.

    2. Material necesario

    • Un equipo con Ubuntu.
    • Un usuario con permisos para ejecutar los comandos de la práctica.
    • Un terminal.
    • Python 3, que normalmente está instalado en Ubuntu.

    No es necesario instalar ni configurar un servidor web permanente.

    3. Actividad 1. Consultar los sockets TCP

    Abre una terminal y ejecuta:

    ss -lnt

    Este comando muestra sockets TCP en escucha.

    Las opciones son:

    • -l: sockets en escucha.
    • -n: direcciones y puertos numéricos.
    • -t: sockets TCP.

    Observa la salida y responde:

    1. ¿Qué puertos aparecen?
    2. ¿Qué direcciones locales aparecen?
    3. ¿Aparece el puerto 22, normalmente asociado a SSH?
    4. ¿Puedes afirmar que un servicio no existe si no aparece en la lista?

    Importante: la salida depende de los servicios que estén ejecutándose en cada equipo. No todos los ordenadores mostrarán los mismos puertos.

    4. Actividad 2. Consultar los sockets UDP

    Ejecuta:

    ss -lnu

    Responde:

    1. ¿Qué diferencia hay entre este comando y ss -lnt?
    2. ¿Aparecen puertos UDP?
    3. ¿Por qué no todos los servicios utilizan TCP?

    UDP no establece una conexión equivalente a TCP. Por eso, sus sockets no se interpretan con los mismos estados de conexión.

    5. Actividad 3. Consultar las conexiones TCP

    Ejecuta:

    ss -ant

    Este comando muestra sockets TCP, incluidos los que están escuchando y las conexiones que tienen otros estados.

    Identifica, si aparecen:

    • LISTEN: socket preparado para aceptar conexiones.
    • ESTAB: conexión TCP establecida.
    • Otros estados, si existen.

    Responde:

    1. ¿Aparece algún socket en estado LISTEN?
    2. ¿Aparece alguna conexión ESTAB?
    3. ¿Qué diferencia hay entre ambos estados?
    4. ¿Por qué la salida puede cambiar mientras utilizas el equipo?

    Si no aparece ninguna conexión establecida, continúa con la siguiente actividad. No es necesario que el equipo tenga conexiones activas para completar la práctica.

    6. Actividad 4. Iniciar un servidor web temporal

    Vamos a utilizar el servidor HTTP sencillo que incluye Python.

    En una terminal, ejecuta:

    python3 -m http.server 8080 --bind 127.0.0.1

    El servidor quedará ejecutándose en primer plano. No cierres esa terminal.

    El comando significa:

    • python3: ejecuta Python 3.
    • -m http.server: ejecuta el módulo que proporciona un servidor HTTP básico.
    • 8080: puerto TCP utilizado por el servidor.
    • --bind 127.0.0.1: limita la escucha a la interfaz de loopback del propio equipo.

    Este servidor sirve archivos del directorio desde el que se ejecuta. Por eso, utiliza un directorio adecuado y no lo ejecutes desde una carpeta con documentos sensibles.

    Comprobar el socket

    Abre una segunda terminal y ejecuta:

    ss -lnt

    Localiza una línea correspondiente al puerto 8080.

    También puedes filtrar el resultado:

    ss -lnt 'sport = :8080'

    Responde:

    1. ¿Qué dirección local aparece?
    2. ¿Qué puerto utiliza el servidor?
    3. ¿Qué estado presenta el socket?
    4. ¿Qué relación existe entre la salida de ss y el servidor Python que acabas de iniciar?

    7. Actividad 5. Acceder al servidor con curl

    En la segunda terminal ejecuta:

    curl http://127.0.0.1:8080

    Deberías recibir una respuesta HTTP con un listado de archivos del directorio servido.

    Ahora ejecuta:

    curl -I http://127.0.0.1:8080

    La opción -I solicita las cabeceras HTTP sin descargar el contenido normal de la página.

    Responde:

    1. ¿Ha respondido el servidor?
    2. ¿Qué código de estado HTTP aparece en las cabeceras?
    3. ¿Qué diferencia hay entre ambos comandos curl?
    4. ¿Qué dirección y puerto utiliza el cliente para llegar al servicio?

    8. Actividad 6. Observar una conexión establecida

    Con el servidor Python todavía en ejecución, abre una terminal y ejecuta:

    curl http://127.0.0.1:8080

    A continuación, consulta:

    ss -ant

    Es posible que la conexión ESTAB no aparezca: curl puede terminar la conexión antes de que ejecutes ss.

    Para mantener una petición activa durante más tiempo, puedes ejecutar:

    curl http://127.0.0.1:8080/archivo-inexistente

    Observa la terminal del servidor y la respuesta de curl. Esta petición puede terminar rápidamente, así que no es obligatorio capturar una conexión establecida.

    Responde:

    1. ¿Qué dirección y puerto corresponden al servidor?
    2. ¿Qué dirección y puerto corresponden al cliente?
    3. ¿Por qué el puerto del cliente puede ser diferente en cada petición?
    4. ¿Por qué una conexión puede desaparecer de ss -ant poco después de una petición?

    9. Actividad 7. Probar una conexión a un puerto sin servicio

    Comprueba si existe un servicio en el puerto 8081:

    ss -lnt 'sport = :8081'

    Si no aparece ningún resultado, no se observa un socket TCP en escucha que coincida con ese filtro.

    Prueba ahora:

    curl --max-time 3 http://127.0.0.1:8081

    Responde:

    1. ¿Se ha completado la petición HTTP?
    2. ¿Qué error muestra curl?
    3. ¿Qué diferencia hay entre una conexión rechazada y una conexión que agota el tiempo de espera?
    4. ¿Podemos concluir que todo el sistema de red está averiado? Justifica tu respuesta.

    El resultado exacto depende del estado del equipo. Un puerto sin servicio puede provocar un rechazo inmediato, pero un cortafuegos u otra circunstancia puede producir un tiempo de espera.

    10. Actividad 8. Cambiar la dirección de escucha

    Detén el servidor Python de la primera terminal con:

    Ctrl + C

    Vuelve a iniciarlo, esta vez escuchando en todas las interfaces IPv4:

    python3 -m http.server 8080 --bind 0.0.0.0

    En la segunda terminal ejecuta:

    ss -lnt 'sport = :8080'

    Compara la dirección local con la obtenida en la actividad 4.

    Responde:

    1. ¿Qué dirección aparece ahora?
    2. ¿Qué significa 0.0.0.0 en este contexto?
    3. ¿Qué diferencia hay entre escuchar en 127.0.0.1 y en 0.0.0.0?
    4. ¿Significa esto que cualquier equipo de Internet puede acceder al servidor?

    Precaución: al escuchar en 0.0.0.0, el servicio puede aceptar conexiones dirigidas a las interfaces IPv4 locales, siempre que la red y el cortafuegos lo permitan. Haz esta prueba solo en un entorno controlado y no publiques el servicio en Internet.

    11. Actividad 9. Probar el acceso desde otro equipo (opcional)

    Realiza esta actividad únicamente si dispones de dos equipos conectados a la misma red y tienes autorización para probar la conectividad.

    En el equipo servidor, averigua su dirección IPv4 con:

    ip -4 addr

    Busca la dirección de la interfaz de red correspondiente a la LAN. No utilices 127.0.0.1 para acceder desde el otro equipo.

    Desde el cliente, ejecuta, sustituyendo la IP por la dirección real del servidor:

    curl --max-time 5 http://IP_DEL_SERVIDOR:8080

    Responde:

    1. ¿Has recibido una respuesta HTTP?
    2. Si no funciona, ¿qué comprobarías antes de concluir que el socket está mal configurado?
    3. ¿Qué diferencias hay entre la dirección de escucha, la dirección de destino y el puerto de destino?

    Si la prueba falla, revisa la IP, la conectividad entre equipos, el cortafuegos y la dirección de escucha. No desactives el cortafuegos como primera medida de diagnóstico.

    12. Finalizar la práctica

    Detén el servidor Python con Ctrl + C en la terminal donde se está ejecutando.

    Comprueba que ya no aparece el puerto 8080:

    ss -lnt 'sport = :8080'

    Si no hay otro servicio utilizando ese puerto, el filtro no debería mostrar resultados.

    13. Entrega

    Entrega un documento que incluya:

    1. Las salidas de ss -lnt, ss -lnu y ss -ant.
    2. Una captura de la escucha en 127.0.0.1:8080.
    3. La respuesta obtenida con curl.
    4. Una comparación entre las direcciones 127.0.0.1 y 0.0.0.0.
    5. Las respuestas a las preguntas de las actividades.
    6. Una conclusión breve que explique la relación entre sockets, puertos, aplicaciones y conexiones.

    14. Rúbrica de evaluación

    Criterio Puntuación
    Consulta e interpretación de sockets TCP y UDP 2 puntos
    Identificación de estados y puertos 2 puntos
    Inicio y comprobación del servidor HTTP 2 puntos
    Comprensión de 127.0.0.1 y 0.0.0.0 2 puntos
    Respuestas, evidencias y conclusión 2 puntos
    Total 10 puntos

    Conclusión

    Un socket permite a una aplicación utilizar los mecanismos de comunicación del sistema operativo. Con ss podemos inspeccionar sockets y conexiones; con curl podemos comprobar si un servicio HTTP responde. Sin embargo, que exista un socket en escucha no garantiza por sí solo que el servicio sea accesible desde otros equipos.
