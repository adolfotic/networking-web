    Tema 4. Ejercicios guiados: Sockets

    Objetivos

    Al terminar estos ejercicios, deberías ser capaz de:

    • Explicar qué es un socket y qué relación tiene con una IP y un puerto.
    • Interpretar direcciones como 192.168.1.20:8080.
    • Diferenciar sockets de escucha y sockets establecidos.
    • Consultar sockets en Ubuntu mediante el comando ss.
    • Comprender cómo un servidor puede atender a varios clientes.
    • Relacionar los sockets con los servicios web y las conexiones TCP.

    Ejercicio 1. Identificar IP, puerto y socket

    Un ordenador tiene la dirección IP 192.168.1.20 y ejecuta un servidor web que escucha en el puerto 8080.

    Preguntas:

    1. ¿Cuál es la dirección IP del ordenador?
    2. ¿Qué puerto utiliza el servidor web?
    3. ¿Qué identifica la combinación 192.168.1.20:8080?
    4. ¿Es lo mismo una IP que un socket?
    Ver solución 1. La IP es `192.168.1.20`. 2. El puerto es `8080`. 3. Identifica un extremo de comunicación asociado a una dirección IP y un puerto, dentro del contexto del protocolo utilizado. 4. No. La IP identifica una interfaz de red; el puerto identifica un extremo lógico de comunicación dentro del sistema. Un socket es un extremo de comunicación gestionado por el sistema operativo. En una conexión real también importa el protocolo, por ejemplo TCP o UDP.

    Ejercicio 2. Interpretar una conexión TCP

    Un navegador de un ordenador 192.168.1.50 se conecta a un servidor web 192.168.1.20 por el puerto TCP 80.

    La conexión utiliza el puerto de origen 53124.

    Preguntas:

    1. ¿Cuál es la IP de origen?
    2. ¿Cuál es el puerto de origen?
    3. ¿Cuál es la IP de destino?
    4. ¿Cuál es el puerto de destino?
    5. ¿Por qué el navegador no necesita utilizar el puerto 80 como puerto de origen?
    Ver solución 1. IP de origen: `192.168.1.50`. 2. Puerto de origen: `53124`. 3. IP de destino: `192.168.1.20`. 4. Puerto de destino: `80`. 5. El puerto 80 es el puerto de destino del servicio web. El cliente suele utilizar un puerto local temporal, asignado para esa conexión. La comunicación TCP distingue entre los dos extremos. El servidor recibe la petición en el puerto donde escucha y el cliente recibe la respuesta en su propio extremo de la conexión.

    Ejercicio 3. Diferenciar escucha y conexión establecida

    En Ubuntu se ejecuta:

    ss -ant

    Aparecen estas líneas simplificadas:

    State       Local Address:Port    Peer Address:Port
LISTEN      0.0.0.0:80             0.0.0.0:*
ESTAB       192.168.1.20:80        192.168.1.50:53124

    Preguntas:

    1. ¿Qué indica el estado LISTEN?
    2. ¿Qué indica el estado ESTAB?
    3. ¿Qué representa 192.168.1.50:53124 en la segunda línea?
    4. ¿Por qué la primera línea muestra 0.0.0.0:80?
    Ver solución 1. `LISTEN` indica que existe un socket TCP preparado para aceptar conexiones. 2. `ESTAB` significa que hay una conexión TCP establecida. 3. Es el extremo remoto de esa conexión: la IP del cliente y su puerto de origen. 4. En una dirección local de escucha, `0.0.0.0` indica que el servicio acepta conexiones dirigidas a cualquiera de las direcciones IPv4 locales compatibles con esa escucha. No es una dirección IP que se utilice como destino normal desde otro equipo.

    Ejercicio 4. Consultar sockets TCP en Ubuntu

    Ejecuta:

    ss -lnt

    Preguntas:

    1. ¿Qué información muestra el comando?
    2. ¿Qué significa la opción -l?
    3. ¿Qué significa la opción -n?
    4. ¿Qué significa la opción -t?
    5. Si aparece el puerto 22, ¿qué servicio podría estar escuchando?
    Ver solución - `-l`: muestra sockets que están escuchando. - `-n`: muestra direcciones y puertos numéricos, sin intentar traducirlos a nombres. - `-t`: muestra sockets TCP. - El comando permite consultar sockets TCP en escucha. El puerto `22` suele utilizarse para SSH, aunque el puerto por sí solo no demuestra qué aplicación está ejecutándose.

    Ejercicio 5. Comparar TCP y UDP

    Un equipo ejecuta estos comandos:

    ss -lnt

    ss -lnu

    Preguntas:

    1. ¿Qué tipo de sockets muestra el primer comando?
    2. ¿Qué tipo de sockets muestra el segundo?
    3. ¿Por qué no es correcto afirmar que TCP y UDP funcionan exactamente igual?
    4. ¿Puede aparecer un socket UDP sin una conexión equivalente a ESTAB de TCP?
    Ver solución 1. `ss -lnt` muestra sockets TCP en escucha. 2. `ss -lnu` muestra sockets UDP locales, normalmente los que están asociados a puertos en uso y que cumplen el filtro de escucha solicitado. 3. TCP establece una conexión y proporciona un flujo de datos fiable y ordenado. UDP envía datagramas sin establecer una conexión TCP. 4. Sí. UDP no tiene estados de conexión equivalentes a los de TCP. Puede haber sockets UDP vinculados a un puerto sin una conexión establecida.

    Ejercicio 6. ¿Por qué puede atender varios clientes un servidor?

    Un servidor web escucha en:

    192.168.1.20:80

    Dos clientes se conectan desde estos extremos:

    192.168.1.50:53124
192.168.1.60:49820

    Preguntas:

    1. ¿Utilizan ambos clientes el mismo puerto de origen?
    2. ¿Utilizan ambos el mismo puerto de destino?
    3. ¿Cómo puede distinguir el servidor las conexiones?
    4. ¿Necesita el servidor abrir un puerto de escucha diferente para cada cliente?
    Ver solución 1. No. En el ejemplo utilizan puertos de origen diferentes. 2. Sí. Ambos se conectan al puerto 80 del servidor. 3. TCP identifica cada conexión mediante la combinación de protocolo y extremos local y remoto, incluyendo las direcciones IP y los puertos. 4. No. El servidor puede mantener un único puerto de escucha y aceptar numerosas conexiones TCP, cada una con su propio estado de conexión.

    Ejercicio 7. Distinguir el puerto de escucha de los puertos de los clientes

    Un servidor escucha en TCP 8080. Tres clientes se conectan desde puertos temporales distintos.

    Cliente A: 192.168.1.51:51001
Cliente B: 192.168.1.52:51002
Cliente C: 192.168.1.53:51003
Servidor:  192.168.1.20:8080

    Preguntas:

    1. ¿Cuántos puertos de escucha necesita el servidor para este servicio?
    2. ¿Cuántas conexiones TCP puede tener si los tres clientes están conectados?
    3. ¿Qué ocurriría si los tres clientes intentaran usar el mismo puerto de origen?
    4. ¿Qué combinación permite distinguir estas conexiones?
    Ver solución 1. Un puerto de escucha, el `8080`, puede ser suficiente. 2. Puede tener tres conexiones TCP establecidas, además del socket de escucha. 3. No es necesariamente un problema: los clientes están en IP diferentes. Lo importante es que la combinación de los extremos de cada conexión sea distinguible y válida. 4. El protocolo y las direcciones IP y puertos de ambos extremos.

    Ejercicio 8. Relacionar sockets y servicios web

    En un servidor Ubuntu se ejecuta una aplicación web que escucha en 0.0.0.0:8080.

    Un alumno intenta acceder desde otro equipo a:

    http://192.168.1.20:8080

    pero no consigue conectarse.

    Preguntas:

    1. ¿Qué indica que la aplicación escuche en 0.0.0.0:8080?
    2. ¿Garantiza esto que el otro equipo pueda conectarse?
    3. ¿Qué otros elementos deberían comprobarse?
    4. ¿Qué comando permite revisar los sockets TCP en escucha?
    Ver solución 1. La aplicación escucha en el puerto TCP 8080 en las interfaces IPv4 locales compatibles con esa escucha. 2. No. La escucha es necesaria, pero no garantiza por sí sola la conectividad. 3. Hay que comprobar la IP del servidor, la conectividad de red, las reglas del cortafuegos, el aislamiento de la red y que la aplicación siga funcionando. 4. Se puede utilizar: 
    ss -lnt
    También puede comprobarse la aplicación desde el propio servidor antes de investigar la red.

    Ejercicio 9. Interpretar un socket local

    Una aplicación de Ubuntu escucha en:

    127.0.0.1:5000

    El navegador del mismo ordenador puede acceder al servicio, pero otro ordenador de la red no puede hacerlo.

    Preguntas:

    1. ¿Qué significa 127.0.0.1?
    2. ¿Por qué puede funcionar desde el propio ordenador?
    3. ¿Por qué no suele funcionar desde otro equipo de la LAN?
    4. ¿Qué debería cambiarse si se quiere permitir el acceso desde la red, suponiendo que el cortafuegos y el resto de la configuración lo permiten?
    Ver solución 1. `127.0.0.1` es una dirección de loopback, utilizada para comunicarse con el propio equipo. 2. El navegador y el servicio están en el mismo sistema. 3. La aplicación está escuchando en la interfaz de loopback, no en la interfaz de red utilizada por los demás equipos. 4. La aplicación tendría que escuchar en la IP de la interfaz de red o, si procede, en `0.0.0.0`. Esto debe hacerse de forma deliberada y con las medidas de seguridad adecuadas.

    Ejercicio 10. Diagnosticar un puerto sin servicio

    Un alumno ejecuta:

    curl --max-time 3 http://127.0.0.1:8081

    El comando devuelve un error de conexión.

    Preguntas:

    1. ¿Qué intenta hacer curl?
    2. ¿Qué indica el error?
    3. ¿Permite asegurar que el equipo no tiene conexión de red?
    4. ¿Cómo comprobarías si existe algún socket TCP escuchando en el puerto 8081?
    Ver solución 1. Intenta realizar una petición HTTP al puerto TCP 8081 del propio equipo. 2. Puede indicar que no hay un servicio escuchando, que la conexión ha sido rechazada o que se ha agotado el tiempo de espera, según el error concreto. 3. No. Solo informa de que esa conexión concreta no se ha completado. No demuestra que la red esté desconectada. 4. Se puede ejecutar: 
    ss -lnt
    Para filtrar el puerto: 
    ss -lnt 'sport = :8081'

    Ejercicio 11. Reto: analizar un servidor web

    En un servidor Ubuntu se ejecuta:

    ss -ant

    Se observan estas líneas:

    State       Local Address:Port    Peer Address:Port
LISTEN      0.0.0.0:8080           0.0.0.0:*
ESTAB       192.168.1.20:8080      192.168.1.51:51001
ESTAB       192.168.1.20:8080      192.168.1.52:51002

    Responde razonadamente:

    1. ¿En qué puerto escucha el servicio?
    2. ¿Cuántas conexiones TCP establecidas aparecen?
    3. ¿Cuántos clientes diferentes se observan?
    4. ¿Por qué las conexiones establecidas no utilizan necesariamente puertos locales diferentes en el servidor?
    5. ¿Qué diferencia hay entre la línea LISTEN y las líneas ESTAB?
    Ver solución 1. En el puerto TCP `8080`. 2. Aparecen dos conexiones establecidas. 3. Se observan dos clientes con IP diferentes. 4. Ambas conexiones usan el puerto local 8080 del servidor. Se distinguen por los extremos remotos y por la combinación completa de la conexión. 5. `LISTEN` representa el socket preparado para aceptar nuevas conexiones. `ESTAB` representa una conexión TCP que ya se ha establecido con un cliente.

    Ejercicio 12. Reto final: explicar una conexión completa

    Un navegador situado en 192.168.1.50 accede a un servidor web situado en 192.168.1.20, puerto TCP 80. El navegador utiliza el puerto local 53124.

    Explica el proceso respondiendo a estas preguntas:

    1. ¿Qué IP y puerto tiene como destino la petición?
    2. ¿Qué IP y puerto utiliza el navegador como origen?
    3. ¿Qué socket permite al servidor aceptar nuevas conexiones?
    4. ¿Qué información distingue la conexión de ese cliente de la de otros clientes?
    5. ¿Qué comando de Ubuntu usarías para observar sockets TCP?
    6. Si el servicio solo escucha en 127.0.0.1:80, ¿podrá conectarse el navegador desde otro equipo de la LAN?
    Ver solución 1. Destino: `192.168.1.20:80`. 2. Origen: `192.168.1.50:53124`. 3. El socket TCP que está en estado de escucha en el puerto 80. 4. La combinación del protocolo y de las direcciones IP y puertos local y remoto. 5. Por ejemplo: 
    ss -ant
    6. No normalmente. Si el servicio escucha solo en `127.0.0.1`, acepta conexiones a través de loopback, no las dirigidas a la interfaz LAN.

    Conclusión

    Recuerda estas ideas:

    • IP: identifica una interfaz de red.
    • Puerto: identifica un extremo lógico de comunicación dentro del sistema.
    • Socket: es un extremo de comunicación gestionado por el sistema operativo.
    • Socket de escucha: permite a un servicio esperar nuevas conexiones.
    • Conexión TCP: relaciona dos extremos y tiene un estado propio.
    • ss: permite inspeccionar sockets y conexiones desde Ubuntu.

    Un puerto abierto o un socket en escucha no garantizan por sí solos que un servicio sea accesible desde otros equipos: también importan la dirección de escucha, la red, el cortafuegos y el estado de la aplicación.
