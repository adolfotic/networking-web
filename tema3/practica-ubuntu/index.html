    Práctica de Ubuntu: puertos y servicios de red

    1. Objetivos

    Al terminar esta práctica, deberás ser capaz de:

    • Consultar los puertos TCP que están en escucha.
    • Diferenciar una dirección de escucha local de una dirección accesible mediante otras interfaces.
    • Identificar conexiones y procesos asociados a los puertos.
    • Realizar peticiones HTTP desde la terminal.
    • Comprobar qué sucede cuando no existe un servicio disponible en un puerto.
    • Explicar por qué un servicio en escucha no tiene por qué ser accesible desde otro equipo.

    2. Material y precauciones

    Necesitarás un equipo con Ubuntu y acceso a una terminal.

    Trabajaremos con comandos de consulta y con un pequeño servidor web de pruebas. No modificaremos las reglas del cortafuegos ni la configuración permanente de red.

    3. Consultar los puertos TCP en escucha

    Ejecuta:

    ss -lnt

    Este comando muestra los sockets TCP que están en escucha.

    Las opciones significan:

    • -l: muestra sockets en escucha.
    • -n: muestra las direcciones y los puertos numéricos.
    • -t: muestra únicamente TCP.

    La salida tendrá un formato parecido a este:

    State   Recv-Q Send-Q Local Address:Port Peer Address:Port
LISTEN  0      128    127.0.0.1:631      0.0.0.0:*
LISTEN  0      128    0.0.0.0:22         0.0.0.0:*

    Es un ejemplo ilustrativo: tu equipo puede mostrar otros puertos o no mostrar ninguno de estos.

    Actividades

    1. ¿Cuántas entradas aparecen en estado LISTEN?
    2. ¿Qué puertos aparecen?
    3. ¿Qué significa LISTEN?
    4. ¿Por qué puede haber diferentes servicios escuchando al mismo tiempo?
    5. ¿Qué diferencia hay entre la dirección local y la dirección del extremo remoto que aparecen en la salida?

    Anota los resultados reales de tu equipo.

    4. Consultar TCP y UDP

    Ahora ejecuta:

    ss -lntu

    En este caso:

    • -l: muestra sockets en escucha.
    • -n: evita resolver nombres de puertos y direcciones.
    • -t: incluye TCP.
    • -u: incluye UDP.

    Observa si aparecen entradas TCP, UDP o ambas.

    Importante: el concepto de escucha no se aplica exactamente igual a TCP y UDP. TCP utiliza un estado de escucha para aceptar conexiones; UDP no establece conexiones TCP, aunque la herramienta puede mostrar sockets UDP preparados para recibir datagramas.

    Actividades

    1. ¿Aparecen más entradas que con ss -lnt?
    2. ¿Qué diferencias observas?
    3. ¿Por qué no todos los puertos que aparecen tienen que corresponder a una conexión activa con otro equipo?

    5. Consultar los procesos asociados

    Ejecuta:

    sudo ss -lntup

    La opción -p permite mostrar información de los procesos asociados a los sockets cuando los permisos y el sistema lo permiten. sudo facilita consultar esa información para procesos de otros usuarios.

    Identifica, si aparecen:

    • El puerto.
    • El protocolo.
    • La dirección local.
    • El nombre o PID del proceso asociado.

    Actividades

    1. ¿Qué procesos aparecen asociados a puertos en escucha?
    2. ¿Reconoces alguno de los servicios?
    3. ¿Por qué algunos procesos pueden no mostrar toda la información si no utilizas permisos suficientes?
    4. ¿Por qué es útil saber qué proceso está utilizando un puerto?

    No detengas ni modifiques servicios del sistema como parte de esta actividad.

    6. Comprender las direcciones de escucha

    Las direcciones de escucha permiten saber en qué interfaces puede recibir tráfico una aplicación.

    Dirección Significado habitual
    127.0.0.1 Interfaz de bucle local IPv4
    0.0.0.0 Todas las interfaces IPv4 locales compatibles con esa escucha
    ::1 Interfaz de bucle local IPv6
    :: Dirección comodín IPv6; su comportamiento respecto a IPv4 depende de la configuración

    Considera estas dos entradas:

    127.0.0.1:8080
0.0.0.0:8080

    Aunque ambas utilizan el puerto 8080, no significan lo mismo.

    • En el primer caso, la aplicación escucha en el bucle local IPv4.
    • En el segundo, la aplicación escucha en todas las direcciones IPv4 locales compatibles con esa configuración.

    Actividades

    1. ¿Cuál de las dos configuraciones permite que la aplicación pueda recibir conexiones dirigidas a una dirección IPv4 de la LAN?
    2. ¿Garantiza 0.0.0.0:8080 que otros equipos puedan acceder al servicio? Justifica tu respuesta.
    3. ¿Qué papel pueden desempeñar el cortafuegos y la configuración de red?
    4. ¿Qué ventaja de seguridad puede tener limitar un servicio a 127.0.0.1?

    7. Crear un servidor web de pruebas

    En este apartado iniciaremos un servidor web temporal utilizando Python. No es necesario instalar paquetes adicionales si Python 3 ya está disponible.

    Paso 1. Comprobar Python

    Ejecuta:

    python3 --version

    Si aparece una versión de Python 3, continúa.

    Paso 2. Crear un directorio de prueba

    mkdir -p ~/prueba-puertos
cd ~/prueba-puertos
echo "Hola desde mi servidor web de pruebas" > index.html

    Explicación:

    • mkdir -p crea el directorio si todavía no existe.
    • cd entra en ese directorio.
    • echo escribe el texto en el archivo index.html.
    • El operador > crea el archivo o sustituye su contenido si ya existía.

    Paso 3. Iniciar el servidor

    Ejecuta:

    python3 -m http.server 8080 --bind 127.0.0.1

    El servidor HTTP de pruebas queda asociado al puerto 8080, pero solo a la dirección de bucle local IPv4.

    Mantén abierta esta terminal. El servidor seguirá funcionando mientras el proceso permanezca activo.

    No cierres la terminal todavía.

    8. Comprobar que el puerto está en escucha

    Abre una segunda terminal y ejecuta:

    ss -lnt

    Busca una entrada parecida a:

    LISTEN 0 5 127.0.0.1:8080 0.0.0.0:*

    La cifra de la cola puede variar según la versión de Python y el sistema.

    Actividades

    1. ¿Aparece ahora el puerto 8080?
    2. ¿En qué dirección está escuchando?
    3. ¿Qué relación existe entre esta entrada y el servidor Python que has iniciado?
    4. ¿Qué diferencia hay entre esta escucha y una que apareciera en 0.0.0.0:8080?

    9. Realizar una petición HTTP con curl

    En la segunda terminal, ejecuta:

    curl http://127.0.0.1:8080/

    Deberías recibir el contenido del archivo HTML:

    Hola desde mi servidor web de pruebas

    El comando curl realiza una petición HTTP a la dirección indicada y muestra la respuesta recibida.

    Ahora prueba:

    curl -I http://127.0.0.1:8080/

    La opción -I solicita las cabeceras de la respuesta HTTP, sin mostrar el cuerpo de la página. La salida incluirá una línea de estado y cabeceras, que pueden variar según la versión y la configuración del servidor.

    Actividades

    1. ¿Qué contenido devuelve la primera petición?
    2. ¿Qué muestra la segunda petición?
    3. ¿Qué diferencia hay entre consultar un puerto con ss y realizar una petición con curl?
    4. ¿Qué demuestra una respuesta HTTP correcta?
    5. ¿Demuestra que el servidor sea accesible desde Internet?

    10. Probar un puerto sin servicio

    Mantén el servidor funcionando en el puerto 8080 y ejecuta en la segunda terminal:

    curl --max-time 3 http://127.0.0.1:8081/

    El puerto 8081 no corresponde al servidor que acabamos de iniciar, salvo que otro programa ya lo esté utilizando.

    Es posible que curl informe de que no puede establecer la conexión. El mensaje exacto depende de la situación del sistema.

    Actividades

    1. ¿Qué diferencia hay entre los resultados de los puertos 8080 y 8081?
    2. ¿Por qué la petición al puerto 8081 no devuelve el contenido de nuestra página?
    3. ¿Podemos concluir que el puerto 8081 está bloqueado por un cortafuegos? Explica por qué no.
    4. ¿Qué comando utilizarías para comprobar si existe una aplicación escuchando en el puerto 8081?

    11. Detener el servidor de pruebas

    Vuelve a la terminal en la que ejecutaste el servidor Python y pulsa:

    Ctrl + C

    El proceso finalizará.

    Después, en la segunda terminal, ejecuta:

    ss -lnt

    Comprueba si el puerto 8080 continúa en escucha.

    Actividades

    1. ¿Ha desaparecido la entrada del puerto 8080?
    2. ¿Por qué ha cambiado la salida de ss?
    3. ¿Qué diferencia hay entre detener el servicio y bloquear su puerto mediante un cortafuegos?

    Si el puerto continúa en escucha, comprueba si existe otro proceso que lo esté utilizando.

    12. Reto opcional: escuchar en la interfaz de red

    Este apartado debe realizarse únicamente en un entorno de prácticas controlado y con autorización del profesor.

    El servidor anterior estaba limitado a 127.0.0.1, por lo que otro equipo no puede acceder normalmente a él mediante la IP LAN del servidor.

    Si el profesor autoriza la prueba, detén primero el servidor y vuelve a iniciarlo con:

    python3 -m http.server 8080 --bind 0.0.0.0

    Este comando permite que el servidor escuche en las interfaces IPv4 locales compatibles, en lugar de limitarse al bucle local.

    Consulta la salida de:

    ss -lnt

    Identifica la nueva dirección de escucha.

    Si la práctica se realiza en una LAN aislada y el profesor lo autoriza, puede probarse desde otro equipo mediante:

    http://IP_DEL_SERVIDOR:8080/

    Sustituye IP_DEL_SERVIDOR por la dirección IPv4 real del equipo que ejecuta Python.

    No expongas este servidor de pruebas a Internet ni cambies reglas del cortafuegos para hacerlo accesible. El servidor de Python es únicamente una herramienta didáctica, no un servidor de producción.

    Al terminar, pulsa Ctrl + C para detenerlo.

    Preguntas del reto

    1. ¿Qué cambio observas en la dirección de escucha?
    2. ¿Por qué ahora podría ser posible acceder desde otro equipo de la LAN?
    3. ¿Qué circunstancias podrían impedir el acceso aunque aparezca 0.0.0.0:8080?
    4. ¿Por qué no es recomendable escuchar en todas las interfaces sin valorar antes los riesgos?

    13. Conclusiones

    Responde con tus propias palabras:

    1. ¿Qué información proporciona ss -lnt?
    2. ¿Qué diferencia hay entre 127.0.0.1 y 0.0.0.0?
    3. ¿Qué función cumple curl en esta práctica?
    4. ¿Qué demuestra que el servidor responda a una petición HTTP?
    5. ¿Por qué un servicio en escucha no tiene por qué ser accesible desde otro equipo?
    6. ¿Qué medidas tomarías antes de exponer un servicio a una red?

    14. Entrega

    Entrega un documento que incluya:

    • Las salidas relevantes de ss -lnt antes, durante y después de iniciar el servidor.
    • Los resultados de las peticiones curl.
    • Las respuestas a las actividades.
    • Las conclusiones finales.
    • Si has realizado el reto opcional, explica las diferencias entre escuchar en 127.0.0.1 y en 0.0.0.0.

    Criterio Puntuación
